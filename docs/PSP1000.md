# PSP-1000-Version — technische Planungsgrundlage

## Festlegung

**Zielplattform ist die PSP-1000** (erstes PSP-Modell, „Fat“). Dieses Dokument sammelt die technischen Rahmenbedingungen und daraus abgeleitete Planungsvorschläge. Es enthält keinen Spielcode. Alles außer der Plattformwahl ist als Vorschlag oder offene Entscheidung gekennzeichnet.

Die PSP-1000 ist das leistungsschwächste PSP-Modell. Ein Spiel, das auf ihr läuft, läuft auch auf PSP-2000, PSP-3000 und PSP Go. Umgekehrt gilt das nicht, weil spätere Modelle doppelt so viel Arbeitsspeicher besitzen.

## Hardware-Rahmen

| Bereich | PSP-1000 | Folge für die Planung |
| --- | --- | --- |
| Prozessor | MIPS Allegrex, 1–333 MHz (Standard 222 MHz) | Für das Spiel 333 MHz einplanen, Akkulaufzeit beachten |
| Arbeitsspeicher | 32 MB, davon für Homebrew im Benutzermodus etwa 24 MB nutzbar | Strenges Speicherbudget, Inhalte pro Bereich laden |
| Grafikspeicher | 2 MB eDRAM | Bildpuffer und häufig genutzte Texturen müssen hineinpassen |
| Grafikeinheit | „Graphics Engine“, 2D und 3D in Hardware | Sprites als texturierte Rechtecke zeichnen |
| Bildschirm | 4,3 Zoll, 480 × 272 Pixel, 16:9 | Lesbarkeit auf kleiner Fläche ist entscheidend |
| Texturen | Seitenlängen als Zweierpotenz, höchstens 512 × 512 | Grafiken in passende Atlanten packen |
| Ton | Stereo-Lautsprecher, Kopfhörerausgang | Akustische Angriffssignale möglich |
| Speichermedium | Memory Stick Pro Duo | Spielstände und Homebrew-Installation |
| Eingabe | Steuerkreuz, Analog-Stick, ✕ ○ □ △, L, R, Start, Select | Keine zweiten Schultertasten, kein zweiter Stick |

Das LCD der PSP-1000 neigt bei schnellen Bewegungen sichtbar zum Nachziehen. Für ein Spiel, das auf Timing und lesbaren Angriffssignalen beruht, ist das wichtig: Signale sollten nicht nur aus kurzen Blitzen bestehen.

## Bezug zum Spielkonzept

### Lernschleife und Timing

Die Lernschleife setzt voraus, dass dieselbe Eingabe im selben Moment immer dasselbe Ergebnis hat. Daraus folgen diese Vorschläge:

- **Feste Bildrate.** 60 Bilder pro Sekunde anstreben. Wenn das nicht stabil erreichbar ist, lieber durchgehend 30 als schwankende Werte.
- **Spiellogik in festen Zeitschritten.** Timingfenster werden in Bildern gezählt, nicht in gemessener Zeit. Dann bleibt ein gelerntes Muster verlässlich.
- **Lesbare Ankündigungen.** Angriffe kündigen sich über Haltung, Silhouette und Ton an und bleiben einige Bilder lang sichtbar. Ein einzelnes Aufblitzen reicht wegen des Nachziehens nicht.

### Rückkehr in den Thronsaal

Der schnelle Neuversuch ist ein Kern des Konzepts. Lange Ladezeiten würden ihn stören.

- **Vorschlag:** Den Thronsaal klein halten und dauerhaft im Speicher lassen. Die Daten der aktuellen Begegnung bleiben ebenfalls geladen, damit ein Neuversuch ohne erneutes Laden beginnt.
- Der Rückkehrkommentar des Helden kann gleichzeitig Wartezeit überbrücken, darf sie aber nicht ersetzen.

### Darstellung der Figuren

Bei 272 Pixeln Bildhöhe muss die Silhouette tragen:

- Die Königin als hohe, monumentale Figur mit klarer Kronenform. Die begrenzten Akzentfarben aus [KOENIGIN.md](KOENIGIN.md) passen gut zu kleinen Darstellungen.
- Der Held als kompakte Figur im grünen Kapuzenumhang. Der dunkle Gesichtsbereich ist auf dem kleinen Bildschirm leicht umzusetzen.
- Die Farbpalette sollte früh auf dem echten Gerät oder im Emulator geprüft werden, weil dunkle Töne auf dem PSP-1000-Display leicht ineinanderlaufen.

### Texte und Dialoge

- Rückkehrkommentare sind kurz. Das passt zu einer Textbox am unteren Bildrand.
- Die Schrift muss deutsche Umlaute und „ß“ enthalten und bei kleiner Größe lesbar sein.
- **Vorschlag:** Eine eigene Bitmap-Schrift mit festem Zeichensatz.

## Steuerung — Vorschlag

| Taste | Belegung |
| --- | --- |
| Steuerkreuz / Analog-Stick | Bewegung |
| ✕ | Ausweichen |
| □ | Leichter Angriff |
| △ | Schwerer Angriff |
| ○ | Interaktion, Dialog weiter |
| R | Blocken oder Parieren |
| L | Ziel fixieren |
| Start | Pause |

Diese Belegung ist nur ein Ausgangspunkt. Welche Aktionen der Held überhaupt besitzt, ist im Spielkonzept noch offen.

## Speicherbudget — erster Richtwert

| Bereich | Richtwert |
| --- | --- |
| Programm und Laufzeit | 4 MB |
| Thronsaal (dauerhaft geladen) | 3 MB |
| Aktuelle Begegnung | 8 MB |
| Figuren (Königin, Held) | 4 MB |
| Ton und Musik | 3 MB |
| Reserve | 2 MB |
| **Summe** | **24 MB** |

Die Werte dienen als Orientierung und werden mit der ersten Begegnung überprüft.

## Technische Grundlage — Vorschlag

- **Toolchain:** Das quelloffene PSPSDK aus dem Projekt [pspdev](https://github.com/pspdev) mit GCC für C oder C++.
- **Grafik:** Direkte Nutzung der Grafikbibliothek `sceGu` aus dem PSPSDK. Für 2D-Sprites genügt sie und spart Speicher gegenüber größeren Engines.
- **Test:** Im Emulator PPSSPP während der Entwicklung, regelmäßig zusätzlich auf einer echten PSP-1000.
- **Ausgabe:** Eine `EBOOT.PBP` zum Starten über den Memory Stick.

## Rechtlicher Rahmen

Eine Veröffentlichung auf UMD oder im PlayStation Store ist ohne offizielle Lizenz von Sony nicht möglich. Realistisch ist ein **Homebrew-Spiel**. Es läuft auf einer echten PSP nur mit einer Custom Firmware oder einem vergleichbaren Homebrew-Zugang. Das Spiel darf keine urheberrechtlich geschützten Inhalte von Sony oder Dritten enthalten. Das gilt auch für die bisherigen Referenzbilder.

## Offene Entscheidungen

- 2D-Sprites, vorgerenderte Figuren oder einfache 3D-Modelle?
- Welche Aktionen besitzt der Held, und wie lautet die endgültige Tastenbelegung?
- Ziel 60 oder 30 Bilder pro Sekunde?
- Programmiersprache C oder C++?
- Wird eine Musik- und Tonbibliothek verwendet oder ein eigener Mixer geschrieben?
- Soll das Spiel zusätzlich auf späteren PSP-Modellen zusätzlichen Speicher nutzen?

## Nächste Schritte

1. Darstellungsform festlegen (2D oder 3D).
2. Thronsaal und eine Begegnung als Testszene planen und dabei die Speicherwerte prüfen.
3. Erst nach der Freigabe dieser Planung ein technisches Grundgerüst mit dem PSPSDK anlegen.
